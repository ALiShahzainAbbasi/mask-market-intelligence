## 2. Architecture and implementation inventory

### 2.1 What was intended

`docs/ARCHITECTURE.md` specifies a layered stack (Next.js → FastAPI → Postgres/pgvector + job queue → Python worker → collector/AI/scoring handlers) with 10 domain modules communicating through explicit service interfaces, a `discover → fetch → parse → normalize → persist` collector contract, and a hard evidence-lineage invariant: every score must be reverse-navigable to raw source documents. `docs/MODULARITY.md` describes `research_runner` explicitly as a **thin coordinator** of `MethodExecutor` implementations — "it does not duplicate source, persistence, extraction, scoring, or report rules." `AGENTS.md` (root) states as a binding rule: "LLMs may classify, extract, summarize, and name clusters; they must not calculate methodology scores... Deterministic backend code owns normalization, weighting, scoring, confidence, completeness checks, rankings, and stage gates."

### 2.3 The `research_runner`/`MethodExecutor` gap — confirmed real, root-caused

**[VERIFIED]** `apps/api/src/mask_api/research_runner/executors/` contains exactly two files: `__init__.py` and `census_m1.py`. `grep -rl "executors" scripts/` returns only `scripts/run_census_m1.py`. Every other real-data driver script (`scripts/run_m4_us_hvac_10_99.py`, `run_m5_us_hvac_10_99.py`, `run_m6_us_hvac_10_99.py`, five `run_m7_us_*.py` variants, `run_m9_us_hvac_10_99.py`, and all the Phase 3 `discover_*.py` scripts) imports `method_metrics.calculate_M*` **directly**, bypassing `ResearchRunner`/`MethodExecutor` entirely. Two of these scripts say so explicitly in their own docstrings: *"Not a MethodExecutor yet (M5 has none registered) -- a one-off driver, matching scripts/run_census_m1.py's proof-of-real-wiring pattern."*

**Root cause [INFERRED, well-grounded]:** this is a genuine engineering/process gap, not a design failure or an abandoned idea. `research_runner.runner.ResearchRunner` is real, well-tested (`apps/api/tests/research_runner/test_runner.py`), and fails soft (`MethodRunStatus.UNKNOWN, reason_code="method.executor_unavailable"` for any unregistered method — it does not crash). The team built one working example (`CensusM1Executor`), stated an intention to build more (README.md's own "Next code" section), and then — under real, documented quota/time pressure spanning dozens of `progress.txt` history entries — pivoted to faster one-off scripts and never returned to register the remaining executors. **This means every real M4/M5/M6/M7/M9 score in the project today was produced outside the system's own specified, reusable, tested pipeline.**

## 3. Methodology, scoring, and gate contradictions

**[VERIFIED]** Gate 1 (`docs/RESEARCH_METHODOLOGY.md`, `docs/SCORING.md`, `configs/formulas/v1.yaml:391-395`) requires `[M1, M2, M4, M5, M6, M7, M9]` with `minimum_score: 6.0`. This is flagged for owner decision, not resolved here: either M6 needs to be de-scoped from Gate 1's hard requirement (a methodology change requiring approval), or the Google Ads credential + transport work needs to become a genuine near-term priority, or Gate 1 is understood to be currently unreachable for any market by design until one of those happens.

### 3.2 Gate 2's M8 requirement vs. plan timing — false alarm

**[VERIFIED]** Gate 2 requires M8 interviews; the plan explicitly defers M8 to "finalists only," after all markets clear desk research. Both sides agree — this is sequential, not contradictory. The one real gap: no document commits to when/how many "finalists" will be chosen, so Gate 2 is open-ended, not broken.

### 3.3 Canonical vs. lite/proxy scores — mostly disclosed, one real exception

**[VERIFIED]** HVAC's full-canonical scores are never shown side-by-side with the 14 Phase 3 markets' lite scores in one ranked table — the risk described in the audit brief's hypothesis did not materialize in that specific form. M9's light-proxy status **is** consistently and clearly disclosed everywhere it appears (`"AUTOMATED PROXY ONLY... NOT the real, owner-reviewed M9"` travels with the number into every JSON and report).

**However, M1 is not held to the same disclosure standard.** `m1_light` (the Phase 3 screening version) uses a genuinely different formula — different weights (`business_count 0.40, concentration 0.20, growth 0.20, economic_capacity 0.20` vs. canonical `buyer_pool 0.30, growth 0.20, fragmentation 0.15, economic_capacity 0.20, target_band_match 0.15`), no `fragmentation_share` component at all, and **relative min-max normalization across the current candidate set** instead of the fixed absolute anchors `configs/formulas/v1.yaml` specifies. For the one market scored both ways, the numbers genuinely disagree: canonical M1 (HVAC) = **6.34/10**; `m1_light` (HVAC, used only as a sanity check) = **7.10/10** — a 12% gap on the same market. The generated `phase3_master` Technical Evidence report presents the `M1` column with no "-light" qualifier in its prose, in contrast to M2/M4/M9 in the same document, which are consistently suffixed. **This is a real, fixable reporting-generation defect** (not a formula defect) — the underlying `m1_light` field name is already correctly distinguished internally; the report-generation step simply drops that distinction.

**Separately, real and material:** the Phase 3 master Founder Decision report ranks and tier-classifies all 14 markets ("TIER 1 — STRONG CANDIDATE," etc.) by a composite score computed over only 30–40% of the intended method weight (the `observed_weight_0_1` field, shown in the table above). `docs/SCORING.md` explicitly prohibits exactly this practice for the real overall score: *"must not label it the final score or rank it as though complete."* A coverage-percentage column is shown alongside the rank (a real mitigation), but a numbered 1–14 rank feeding a three-tier strategic recommendation functions, in substance, as ranking-as-though-complete. Concretely: "Car Washes" ranks #3 and lands in Tier 1 on a composite whose `m9_light_proxy` component (weight 0.10 in the screening formula) rests on a single Gemini-judged mention.

### 3.4 Undocumented parallel "screening" weight scale

**[VERIFIED]** `scripts/discover_phase3_deep_dive.py` and `scripts/discover_wave_b_top24.py` both hardcode an identical 5-component weight set (`m1_light 0.30, m2_light 0.25, m4_light 0.20, m7_light 0.15, m9_light 0.10`) that bears no numerical relationship to the frozen `configs/formulas/v1.yaml` overall weights (M1=0.10, M2=0.15, M4=0.15, M7=0.08, M9=0.05) and was never entered into `configs/formulas/` as a versioned, approved configuration.

**[VERIFIED, corrected 2026-09-18 — the original 2026-09-17 draft of this finding conflated four distinct issues; they are separated here per the owner's explicit request not to conflate them.]**

1. **Process approval — exists.** `progress.txt` (AUTONOMOUS-050, 2026-09-15 18:05): *"Owner directive: begin Stage B... confirmed and agreed with the owner in chat before starting: Wave A (free, Census-only, ~40 candidates) first, then Wave B (real multi-source evidence on the ~20-25 survivors) before any full per-market deep-dive."* The two-wave screening **approach** — and the decision to fall back to Wave A's own ranking when Wave B's evidence proved too thin (AUTONOMOUS-051, 2026-09-15 23:58: *"reported to the owner as an explicit decision point, not resolved unilaterally"*) — was genuinely discussed and agreed with the owner in chat. This part is not an approval gap.
2. **Weight-value approval — real gap.** No evidence was found that the owner separately reviewed or approved the specific numeric weight values (`0.30/0.25/0.20/0.15/0.10`, or Wave A's own separate `0.40/0.20/0.20/0.20`) as distinct from approving the general two-wave process. These are an engineering judgment call, never individually surfaced for sign-off.
3. **Versioning — real gap, confirmed.** The weights live only as hardcoded dicts inside two Python scripts, never entered into `configs/formulas/` as a versioned artifact. This is independent of (1) and (2): even a fully-approved weight scheme would still need this fix to be reproducible/auditable.
4. **Documentation — real, distinct gap.** No file under `docs/` (not `SCORING.md`, not `RESEARCH_METHODOLOGY.md`) documents that a screening-weight scheme exists at all, separate from the canonical v1 formulas. The only record of it is inline code comments and `progress.txt` narrative, both of which *do* consistently and honestly label every use as "a pre-screen proxy only, NOT the approved formula" at the point of creation — so this is a documentation-location gap, not a disclosure failure.
5. **Presenting a provisional screening score as canonical — a separate, confirmed defect, not a weight-approval issue at all.** This is the `m1_light`-shown-as-bare-`M1`-in-report-prose issue already described in §3.3/§4 item 1 — a reporting-layer labeling defect, unrelated to whether the underlying weights were approved or versioned.

**Net correction:** the original finding's framing ("unapproved") is too broad. The two-wave screening *process* was approved; the specific *weight values* were not separately reviewed and are not versioned or documented as a distinct artifact — narrower, but still real gaps requiring items (2)-(4) above, not a wholesale re-approval of the screening concept.

A related, low-severity finding: `scripts/aggregate_phase3_master.py:95` uses `float(r["composite_score_0_10"] or 0)` as a sort key — this coerces a genuinely-missing composite to `0.0` only for sort-ordering purposes (the stored/displayed value itself stays `None`), so it is a minor hygiene issue, not a scoring-corruption bug. The real, code-reviewed core (`market_scoring/scoring.py`) correctly excludes missing methods from any weighted sum rather than defaulting them to zero.

### 9.1 New finding: the Capterra review collection was not properly authorized

**[VERIFIED, 2026-09-18]** The original audit characterized Capterra's real robots.txt (which explicitly allows `GPTBot`/`ClaudeBot`) as sufficient authorization to collect and AI-process its review content, in contrast to G2 (correctly rejected for disallowing AI crawlers in robots.txt). This was incomplete. This project's own `docs/SCRAPING_POLICY.md` requires, as a mandatory precondition for any collection (§2, path 4; §4, "Source registration is mandatory"): *"the source policy, **terms**, robots controls, rate limits, and applicable law permit it"* and a recorded *"terms and robots review dates and reviewer"* — terms-of-service review is a named, separate, mandatory requirement alongside a robots.txt check, not satisfied by robots.txt alone. **Only robots.txt was ever checked for Capterra; no terms-of-service review was performed, and no `SourcePolicy` was ever registered for it at all** (confirmed independently in `SOURCE_UTILIZATION_REGISTER.md`).

This pass performed the missing terms-of-service check directly, reading Capterra's live **General User Terms** (`https://www.capterra.com/legal/terms-of-use/`, "Last Updated on May 4, 2026"), Section 10, "PROHIBITED AUTOMATED ACCESS, SCRAPING, AND DATA EXTRACTION," verified by reading the raw page DOM text directly (not an AI-summarized fetch). The real, verbatim clause states users agree not to, without Capterra's express prior written consent:

> *"(a) access, collect, copy, scrape, harvest, cache, index, store, archive, or otherwise extract any content or data from the Service, including user reviews... through automated, programmatic, or mechanical means (including robots, spiders, crawlers, scrapers, headless browsers, data-mining tools, or similar technologies), whether or not such content is publicly accessible; (b) bypass, defeat, avoid, deactivate, impair, or circumvent any access controls... including... robots.txt directives...; (c) use, ingest, incorporate, reproduce, store, analyze, benchmark, or otherwise exploit any content or data obtained from the Service... to train, test, validate, fine-tune, evaluate, or improve any machine-learning model, generative AI system, algorithmic product... whether for internal or external use... You understand and agree that access to the Site is contractually conditioned on compliance with these restrictions, which apply regardless of whether any portion of the Service or its content is publicly viewable."*

This is unambiguous and directly on point: (a) prohibits exactly the browser-based `get_page_text` collection method actually used, explicitly regardless of public accessibility; (b) explicitly states that permissive `robots.txt` directives do **not** override this contractual restriction — directly refuting the original audit's reliance on robots.txt as sufficient; (c) explicitly prohibits using the collected content with a "generative AI system" to "analyze... or evaluate" it — exactly what the Gemini `COMMERCIAL_PAIN_V1` extraction pipeline did to the 32 collected reviews.

**Corrected conclusion:** the Capterra collection performed this session was **not authorized** under the site's own real, current Terms of Use, notwithstanding robots.txt's permissiveness. This is a genuine compliance gap against the project's own `docs/SCRAPING_POLICY.md`, not merely an "unregistered source" engineering backlog item as the original audit characterized it.

- The raw collected files (`outputs/runs/capterra_reviews_raw/*.txt`) and the two extraction runs' outputs (`outputs/runs/phase3_capterra_pain_20260917T132607Z/`, `.../phase3_capterra_pain_20260917T133014Z/`) have **not** been deleted or modified by this audit, per instruction, and remain exactly as they were.
